- **Asumsi / keputusan**:
  1. "Hapus" milik sendiri (deletePost/deleteComment, PRD 18.3.8) DISUPRESI bila viewerRole moderator/admin: menu moderator tidak menampilkan dua "Hapus" berdampingan; mod "Hapus" (modApplyAction delete) menghasilkan soft delete yang sama PLUS tercatat di mod_actions dan menutup laporan open (RPC mod_apply_action, migrasi 0002) — superset fungsional, tidak ada kapabilitas hilang. Untuk member, perilaku lama utuh.
  2. Dialog moderasi dirender INLINE (bukan createPortal seperti ReportDialog) supaya DOM-nya tetap di dalam akar menu: klik luar/dokumen tidak menutup menu di tengah pengisian alasan, dan pesan sukses "di menu" tetap mungkin tampil setelah aksi. Semua tombolnya type="button"+onClick (bukan form submit) sehingga preventDefault pembungkus anti-navigasi-kartu tidak mengganggu; input fokus normal (preventDefault hanya di click, bukan mousedown). Pola visual meniru ConfirmDialog admin (overlay fixed z-50, klik latar/Escape/Batal menutup, nonaktif saat loading).
  3. Pesan sukses mengikuti konteks: hide post → "Post disembunyikan", hide komentar → "Komentar disembunyikan", delete (post/komentar) → "Konten dihapus" — dua string pertama persis kontrak tugas, varian komentar adalah perluasan wajar. Menu TIDAK ditutup otomatis setelah sukses agar pesan sempat terbaca; refresh berikutnya menghilangkan kartu/komentar dari tampilan (view memfilter) sehingga pesan ikut hilang.
  4. Alasan dikirim SELALU non-kosong (trim); kosong → "Takedown langsung oleh moderator" (default kontrak). Placeholder input menampilkan default itu; maxLength 300 (kolom mod_actions.reason bertipe text tanpa batas — batas UI pencegahan saja).
  5. Aksi "restore" sengaja TIDAK ada di menu (instruksi tugas + realitas UI: konten tersembunyi/terhapus tidak tampil di feed/detail karena posts_feed/comments_view memfilternya); deskripsi dialog menyebut pemulihan lewat dashboard admin. Suspend/ban user juga tidak dimasukkan (bukan bagian tugas; tetap di dashboard).
  6. Tipe `ViewerRole` diekspor dari PostMenu (bukan lib/** — milik saya terbatas) dan diimpor type-only di PostCard/CommentTree/FeedList; halaman server cukup memakai `sesi?.role ?? "member"` karena `SessionProfile.role` (UserRole) identik secara struktur dengan ViewerRole — tidak ada impor runtime lib/actions/auth di halaman.
  7. Moderator yang statusnya suspended tetap melihat menu (role di UI hanya kosmetik) — RPC/RLS menolak dengan FORBIDDEN dan pesan itu tampil di dialog; konsisten dengan prinsip "server satu-satunya penjaga".
  8. Dialog pakai `useId()` untuk aria-labelledby & htmlFor agar id tidak bentrok saat satu halaman memuat banyak PostMenu (feed) — hanya satu dialog yang bisa terbuka per menu, tetapi id tetap unik di seluruh dokumen.

- **Cara memeriksa**:
  1. `npm run build` harus lulus (tidak ada tipe baru yang melanggar; semua prop opsional).
  2. Login sebagai moderator/admin → beranda & /c/[slug]: menu titik tiga tiap kartu memuat "Lapor", "Sembunyikan", "Hapus" (tanpa "Hapus" duplikat pada post sendiri). "Sembunyikan" → dialog "Sembunyikan post ini?" + kolom Alasan (opsional) → "Ya, sembunyikan" → menu menampilkan "Post disembunyikan" → setelah refresh kartu hilang dari feed. "Hapus" → dialog "Hapus post ini?" → "Ya, hapus" → "Konten dihapus" → kartu hilang.
  3. Alasan kosong → mod_actions tercatat berisi "Takedown langsung oleh moderator"; alasan diisi → tercatat apa adanya (cek dashboard admin → Log moderasi; laporan open pada target ikut berstatus resolved).
  4. /p/[id] sebagai moderator: PostMenu header punya aksi moderasi; tiap komentar juga punya (lewat CommentTree). Hide/hapus komentar → jadi "[komentar dihapus]" setelah refresh. Hide/hapus post → refresh berikutnya halaman menjadi "Post tidak bisa ditampilkan" (POST_UNAVAILABLE).
  5. Batal/klik latar/Escape menutup dialog (Escape pertama hanya dialog, kedua menutup menu); saat "Memproses..." semua penutupan nonaktif; gagal (mis. moderasi menargetkan konten admin sebagai moderator) → pesan error tampil di dalam dialog, dialog tetap terbuka untuk retry.
  6. Login sebagai member biasa / tamu: menu hanya "Lapor" (+ "Hapus" pada konten sendiri) — TIDAK ada "Sembunyikan"; perilaku lama tidak berubah; /u/[username] juga masih tampil menu lama (lihat kebutuhan ORCHESTRATOR di atas).
  7. Dashboard admin masih bisa memulihkan konten hasil takedown (restore) — verifikasi post/komentar kembali tampil di feed/detail setelah restore.
